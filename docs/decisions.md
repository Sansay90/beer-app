# Решения

Почему brewapp устроен так, а не иначе. Меняя одно из этих решений, допиши сюда новое — со старым и причиной смены.

## Продукт

**Сервис для любых пивоваров, а не под одну пивоварню.** Никаких поправок под конкретный экземпляр или привычки одного пивовара: в пивоварню уходит ровно то, что задано в рецепте; то, что зависит от модели (мощность, шаги), сообщает агент. *Почему:* сервис открытый — у других пивоварен другие модели и другие привычки.

**Рецепты — центр, управление пивоварней — дополнительная возможность.** Каталог и рецепты открыты без входа, пивоварня — после входа и подключения агента. *Почему:* пивоваров с рецептами больше, чем владельцев Easy Brew; пивоварня приводит своих владельцев, рецепты — всех.

**Всё по-русски.** Интерфейс, тексты ошибок, документация, комментарии. *Почему:* сервис для пивоваров СНГ — русскоязычных сервисов рецептов нет, зарубежные есть.

## Устройство

**Сервис + домашний агент.** *Почему:* модуль Tuya принимает команды только в домашней сети и только с ключом устройства, а облако Tuya требует кабинета разработчика. Агент открывает соединение сам — не нужны ни белый IP, ни проброс портов; ключи остаются дома, утечка базы сервиса не даёт доступа к пивоварням. *Цена:* пивовару нужно где-то держать агента (ПК, Raspberry Pi, NAS).

**Агент ↔ сервис — WebSocket с номерами записей и подтверждениями.** *Почему:* соединение рвётся незаметно, а история варки должна быть без дыр; повторы отбрасываются по номеру. Команды при этом не копятся: ТЭН на 2–3 кВт не должен включиться через час по старой команде.

**Программа пивоварни — в общем виде.** Сервис шлёт шаги, таймеры и закладки, агент переводит их в протокол своей пивоварни. *Почему:* другая пивоварня — новый драйвер агента, сервис не меняется.

**Интерфейсу — SSE, а не WebSocket.** *Почему:* интерфейсу нужен поток в одну сторону, команды — обычные POST; SSE переподключается сам и проходит через любой прокси.

## Данные

**Postgres.** *Почему:* у сервиса будут пользователи, их истории варок и пивоварни; SQLite не для этого. SQLModel — схемы и таблицы на Pydantic; схема меняется только миграциями Alembic, они применяются при старте.

**Рецепт — один JSON-документ (JSONB), а не таблицы ингредиентов.** *Почему:* рецепт читают и пишут целиком, а его формат растёт (вода, брожение, фото); по рецепту ищут только по названию и видимости. Формат — по мотивам BeerJSON, чтобы позже были импорт и экспорт. *Цена:* запросы «все рецепты с Citra» — по JSONB, а не по таблице.

**Фото — в Postgres.** *Почему:* проще бэкапить и удалять вместе с рецептом; объёмы пока маленькие. Когда станет много — S3-совместимое хранилище.

**Показатели считают и интерфейс, и сервис.** Интерфейс — на лету в редакторе, сервис — при сохранении, и хранятся показатели сервиса. *Почему:* редактору нужен мгновенный отклик, а каталогу — числа, которым можно верить, кто бы ни прислал рецепт. Чтобы реализации не разошлись, обе проверяются по общим примерам (`shared/`). То же для программы пивоварни.

**Выход экстракта — средний по типу и цвету сырья.** *Почему:* справочника ингредиентов пока нет; появится — выход возьмётся из него.

**Сахар сбраживается целиком.** Сахар, добавленный на брожении, в OG не входит, а в крепость — входит. *Почему:* так сбраживается сахар в жизни; степень сбраживания дрожжей указывают для солодового сусла.

## Вход и права

**Почта и пароль, сессия — в базе, токен — в httpOnly-cookie.** *Почему:* сессию можно отозвать (выход, новый пароль), токен недоступен скриптам страницы. JWT не нужен — сервис один. Telegram и Яндекс ID — позже, дополнительными способами входа.

**Защита от чужих сайтов — `SameSite=Lax` и проверка `Origin`**, без CSRF-токенов. *Почему:* интерфейс и API на одном адресе, а современные браузеры шлют `Origin` с изменяющими запросами.

**Права — в одном модуле (`access.py`), чужие личные рецепты не видит никто, и администратор тоже.** *Почему:* личный рецепт — частные данные; модерации нужны только опубликованные.

## Интерфейс

**Nuxt 4 + Nuxt UI, гибридный рендеринг.** Каталог и страница рецепта рендерятся на сервере Nuxt, личные экраны — приложение в браузере. *Почему:* публичные страницы должны видеть поисковики, а ссылки в мессенджерах — разворачиваться превью; личным экранам (варка с живым потоком, редактор) серверный рендеринг почти ничего не даёт, а сервер слабый. *Было:* одностраничное приложение, которое раздавал сам сервис, одним контейнером (до 27.10.2026). *Цена:* второй контейнер (Node) на сервере, ~100 МБ памяти.

**Интерфейс и API — на одном адресе.** nginx шлёт `/api` сервису, остальное — Nuxt; в разработке `/api` проксирует сам Nuxt. *Почему:* cookie входа и проверка источника без CORS.

**Данные — средствами Nuxt (`useApi`, `useAsyncData`, `$api`), Pinia — только клиентское состояние.** Клиент и типы строит nuxt-open-fetch по OpenAPI сервиса. *Почему:* ключи, кэш, состояние загрузки и SSR — из коробки; типы API не пишутся руками и не расходятся с сервисом.

## Сборка и выкатка

**Свой образ у каждого приложения: сервис, интерфейс, агент** (`service/`, `web/`, `agent/` — у каждого свой `Dockerfile`). *Почему:* они запускаются и обновляются независимо; агент живёт дома и ставится сам по себе.

**Образ собирается в GitHub Actions, на сервер приходит готовым.** *Почему:* сборке интерфейса нужно больше памяти, чем у сервера; выкатка — `docker compose pull && up`. Каждый пуш в `main` проходит линтеры и тесты до выкатки.
