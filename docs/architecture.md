# Как устроен brewapp

Сервис рецептов для домашних пивоваров с управлением пивоварней Easy Brew Connect. Здесь — устройство на сегодня; что умеет — [features.md](./features.md), куда идём — [roadmap.md](./roadmap.md), как вести разработку — [development.md](./development.md).

```
браузер, телефон ──HTTPS──▶ nginx ─┬─ страницы ──▶ web: сервер Nuxt ──/api──┐
                                   └─ /api: API + SSE ──────────────────────┴─▶ сервис ◀──WSS── агент ──Tuya 3.4──▶ пивоварня
                                                                               FastAPI         дома, рядом
                                                                               Postgres        с пивоварней
```

| Папка | Что это |
|---|---|
| `service/` | сервис: API, поток SSE, WebSocket для агентов, Postgres |
| `agent/` | агент: держит подключение к пивоварне по домашней сети и сам подключается к сервису |
| `web/` | интерфейс: Nuxt 4 + Nuxt UI; публичные страницы рендерит сервер Nuxt, личные — приложение в браузере |
| `shared/` | общие примеры расчётов и программы пивоварни — по ним проверяют себя и сервис, и интерфейс |
| `deploy/` | сервер: compose, nginx, настройка; образы — `service/Dockerfile`, `web/Dockerfile` (агент — `agent/Dockerfile`) |

Пивоварню из интернета не достать: модуль Tuya принимает команды только в домашней сети и только с ключом устройства. Поэтому рядом с пивоварней работает агент, а соединение с сервисом открывает он сам — пивовару не нужны ни белый IP, ни проброс портов. Ключи Tuya остаются у агента: утечка базы сервиса не даёт доступа к пивоварням.

## Сервис

FastAPI, Postgres (SQLModel, миграции Alembic), Python 3.13. Код — пакет `service/app`, разделы — подпакетами:

```
app/
  main.py        сборка приложения: create_app(), lifespan, роутеры, раздача интерфейса
  cli.py         python -m app: serve · agents new|list · vapid · openapi
  config.py      настройки — переменные окружения или service/.env (pydantic-settings)
  deps.py        общие объекты из app.state — зависимости для роутеров
  errors.py      ошибки предметной области → HTTP-статус (Invalid 400, Forbidden 403, NotFound 404, Conflict 409)
  access.py      роли и права — в одном месте
  security.py    изменяющие запросы — только со своего сайта (проверка Origin)
  db.py          подключение и миграции · models.py — таблицы · schemas.py — общие схемы API
  mail.py        письма (SMTP; без него — в журнал) · web.py — раздача собранного интерфейса
  auth/          вход: пароли, сессии и ссылки из писем, лимиты попыток, пользователи и роли; роутеры /auth и /admin
  recipes/       рецепты: хранение и права (store), программа пивоварни (program), показатели (calc), фото; роутер
  brewery/       пивоварни: агенты на связи (hub), устройства, журнал варок, поток SSE, команды (control); роутер
  push/          уведомления Web Push: подписки и отправка
```

**Запрос** проходит так: роутер раздела → зависимости говорят, *кто* спрашивает (`Viewer` — гость или пользователь, `CurrentUser`, `Admin`) и *с чем* работать (`RecipeStore` глазами этого человека, `Brewery` — его пивоварня) → модуль данных выполняет и при отказе бросает ошибку из `errors.py` → общий обработчик превращает её в ответ `{"detail": "текст для человека"}`. Роутеры исключения в HTTP вручную не переводят.

**Состояние процесса** — в `app.state`, глобальных переменных нет. При сборке приложения туда кладутся настройки, почта и лимиты входа, на старте (lifespan) — журнал, хранилище пивоварен, `Hub`, подписчики SSE и рассылка уведомлений. Тесты поднимают сколько угодно независимых экземпляров сервиса.

**Фоновые потоки.** Журнал пивоварен (температура, события, варки) пишется в базу своим потоком через очередь: медленная база не тормозит приём от агентов. Уведомления и письма тоже уходят своими потоками.

## Агент

Python, tinytuya, websockets. Пакет `agent/agent`:

```
agent/
  __main__.py    запуск · config.py — настройки (окружение или agent/.env)
  device.py      подключение к пивоварне: свой поток, сторож связи, команды с проверкой эха
  controller.py  смысл поверх DP: состояние, таймер шага, закладки, события, варки
  energy.py      оценка расхода электричества ТЭНом
  recipe.py      программа ↔ бинарный блок рецепта (DP 128)
  link.py        связь с сервисом: переподключение, неподтверждённые записи, команды
  state.py       память между перезапусками (data/state.json)
  fake.py        имитация пивоварни — для тестов
```

Протокол пивоварни (DP, формат рецепта, поведение на нагреве) — [agent/PROTOCOL.md](../agent/PROTOCOL.md).

## Сервис ↔ агент

WebSocket `/api/agent`, токен агента — в заголовке `Authorization`. Сообщения — [agent/README.md, «Протокол»](../agent/README.md#протокол). Главное:

- **Записи не теряются.** События, температура и варки пронумерованы (`seq`) и лежат у агента, пока сервис не подтвердит номер (`ack`). Ушедшее в незаметно оборвавшееся соединение после переподключения уходит снова, повторы сервис отбрасывает.
- **Варка, конец которой ещё в пути, не закрывается.** В `hello` агент перечисляет варки, по которым у него остались недосланные записи, — их сервис не закрывает как прерванные.
- **Команды не копятся.** Агента нет на связи — сразу 503 «пивоварня не в сети»; старая команда не сработает через час, когда агент переподключится. Связь оборвалась посреди команды — тоже 503, с оговоркой: пивоварня могла её выполнить.
- **Программа — в общем виде.** Сервис шлёт шаги, минуты таймеров и что класть по каждому; как записать это в пивоварню, решает агент. Другая пивоварня — новый драйвер агента, сервис не меняется.

## Пивоварня ↔ интерфейс

```
пивоварня ─DP─▶ агент: Controller ─state/event─▶ сервис: Hub ─▶ Streams ─SSE /api/stream─▶ вкладки владельца
                                                           └─▶ Journal (база), Pusher (уведомления)
кнопка в интерфейсе ─POST /api/…─▶ Brewery.run ─▶ Hub.command ─WS─▶ агент ─▶ пивоварня ─эхо DP─▶ ответ
```

Ответ агента на команду — как HTTP-статус: 400 неверные данные, 404 нет такого, 502 пивоварня не подтвердила, 504 не ответила.

## Рецепт, программа и показатели

Рецепт описывает пиво (по мотивам BeerJSON): стиль, партия, засыпь, хмель, добавки, дрожжи, вода, затирание, кипячение, брожение. Хранится целиком в JSONB.

- **Программа пивоварни** выводится из рецепта: паузы затирания, кипячение, таймеры закладок и что класть по каждому. Вирпул — напоминание в конце кипячения, с временем выдержки. Сервис — `recipes/program.py` (для агента), интерфейс — `web/app/utils/recipe.ts` (для экрана). Правила одни.
- **Показатели** (OG, FG, ABV, IBU по Tinseth, цвет по Morey) считаются по ингредиентам. Сахар сбраживается целиком, где бы его ни добавили; добавленный на брожении в OG (плотность сусла до дрожжей) не входит, а в крепость — входит. Интерфейс — на лету в редакторе (`web/app/utils/calc.ts`), сервис — при сохранении (`recipes/calc.py`), и в базу идут показатели сервиса: присланные клиентом не сохраняются.
- **Обе пары реализаций** проверяют себя по одним и тем же примерам — `shared/calc-cases.json` и `shared/program-cases.json` (тесты `service/tests/test_shared.py` и `web/test/unit/shared.test.ts`). Меняешь правило — меняешь обе стороны и примеры.

## Вход и права

- **Вход** — почта и пароль (scrypt), сессия — случайный токен в httpOnly-cookie, в базе — его SHA-256; 30 дней с последнего захода. Ссылки из писем (подтверждение почты, новый пароль) — одноразовые токены со сроком.
- **Роли** (`access.py`): гость — опубликованные рецепты и фото; пользователь — свои рецепты (публиковать — с подтверждённой почтой), своя пивоварня, варки, уведомления; администратор — ещё снимает с публикации и удаляет чужие опубликованные рецепты и раздаёт роли. Чужие личные рецепты не видит никто. Интерфейс только прячет недоступные кнопки — решает сервис.
- **Защита:** лимиты попыток входа и писем (`auth/throttle.py`), изменяющие запросы — только со своего сайта (`security.py`), ссылки в письмах — только на `APP_URL`.

## Данные

```
users ─┬─ sessions                  входы: токен cookie — хэшем
       ├─ auth_tokens               ссылки из писем
       ├─ agents                    агенты у пивоварен: токен — хэшем, когда были на связи
       ├─ devices ─┬─ readings      температура во времени
       │           ├─ events        события пивоварни
       │           └─ brews         варки: снимок рецепта, начало, конец, исход, расход электричества
       ├─ recipes                   рецепт целиком — JSONB; личный или опубликованный
       │    └─ recipe_photos        фото пива и превью
       └─ push_subscriptions        браузеры, подписанные на уведомления
```

Пивоварня в базе — то, что нужно без агента на связи: модель, ограничения, профиль оборудования. Ключи Tuya, адрес и память о программе — только у агента. Схема меняется только миграциями Alembic; они применяются при старте сервиса.

## Интерфейс

Nuxt 4 + Nuxt UI, Pinia; работает своим сервером Nuxt (Nitro, Node). **Гибридный рендеринг:** каталог и страница рецепта рендерятся на сервере — их видят поисковики, ссылки в мессенджерах разворачиваются превью (мета-теги); личные экраны (варка, редактор, настройки, администрирование, вход) — приложение в браузере (`routeRules`, `ssr: false`). `/api` у интерфейса — тот же адрес: в проде nginx шлёт его сервису, в разработке и при рендеринге на сервере — прокси Nuxt (`NUXT_API_SERVER`); cookie входа доходит до сервиса и при серверном рендеринге. Данные — средствами Nuxt: `useApi` / `useAsyncData` для чтения, `$api` для изменений; клиент и типы строит nuxt-open-fetch по OpenAPI сервиса (`npm run api:types`), руками не пишутся. Pinia — только клиентское состояние: кто вошёл, живое состояние пивоварни из SSE, настройки. Устройство — [web/README.md](../web/README.md).

## Проверки и выкатка

- **Тесты.** Сервис (`service/tests`, pytest): сквозные — настоящий сервис в потоке, настоящая база, агент с имитацией пивоварни: вход и роли, рецепты и фото, варка от загрузки рецепта до конца программы, перезапуск агента и сервиса посреди варки, зависшее соединение; юнит — программа, расчёты, фото, лимиты. Агент (`agent/tests`): кодирование программы, контроллер на имитации пивоварни, связь с поддельным сервисом. Интерфейс (`web/test/unit`, vitest): утилиты расчётов, воды, рецепта и варки.
- **Линтеры:** ruff (Python), ESLint с правилами Nuxt (интерфейс), проверка типов (`nuxt typecheck`).
- **CI** (`.github/workflows/deploy.yml`): на каждый пуш и pull request — линтеры, тесты, сверка схемы API с типами интерфейса; пуш в `main` после проверки собирается в образ и выкатывается на сервер — [deploy/README.md](../deploy/README.md).
