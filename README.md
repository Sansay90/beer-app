# brewapp — рецепты и пивоварня Easy Brew

Приложение для домашних пивоваров: рецепты с расчётом показателей, воды и фото пива, история варок и управление пивоварней Easy Brew Connect (Wi-Fi через модуль Tuya; штатное приложение — Smart Life). С пивоварней говорит агент по домашней сети, без облака Tuya и без замены прошивки; Smart Life продолжает работать параллельно.

Куда идёт проект — [ARCHITECTURE.md](./ARCHITECTURE.md): открытый сервис рецептов для пивоваров СНГ, пивоварня подключается через домашний агент.

```
web/ (Nuxt)  ──HTTP + SSE──▶  service/ (Python, Postgres)  ◀──WebSocket──  agent/ (Python)  ──Tuya 3.4──▶  пивоварня
```

Три самостоятельных приложения:

- **[service/](./service/README.md)** — сервис (бэкенд): рецепты, фото, история варок, уведомления. Интерфейсу отдаёт состояние пивоварни потоком SSE и принимает команды, пивоварне передаёт их через её агента. Данные — в Postgres. Запускается в Docker Compose или локально из `.venv` с базой в Docker.
- **[agent/](./agent/README.md)** — агент рядом с пивоварней: держит подключение к ней по домашней сети и сам открывает соединение с сервисом — ни белый IP, ни проброс портов не нужны. Ключи Tuya остаются у него. Протокол пивоварни — [agent/PROTOCOL.md](./agent/PROTOCOL.md).
- **web/** — интерфейс: Nuxt 4 + Nuxt UI, Pinia, типизированный клиент API из OpenAPI сервиса. Статическая сборка раздаётся сервисом, позже упаковывается в PWA / Capacitor.

## Запуск

**Каждый день** — двойной клик по **`start.bat`**: сервис и агент стартуют в свёрнутых окнах, интерфейс открывается отдельным окном Edge (нужна сборка `web`, см. ниже). Либо всё в Docker (`service/`: `docker compose up -d` — база, сервис и агент) — тогда сервис отдаёт только API, а интерфейс — из `web` (`npm run dev`).

Первый запуск: `.env` для сервиса и агента (образцы — `.env.example`), токен агента — `python -m app.agents new` в `service`, ключи пивоварни — [agent/README.md](./agent/README.md#ключи-пивоварни-один-раз).

**В интернете** — https://151-243-208-72.sslip.io: каждый пуш в `main` проверяется, собирается в образ и выкатывается на сервер сам — [deploy/README.md](./deploy/README.md).

**Вход и роли**: гость смотрит опубликованные рецепты, вход — по почте (выдвижная панель), пользователь ведёт свои рецепты и свою пивоварню, администратор ещё модерирует и раздаёт роли — [service/README.md](./service/README.md#вход-и-роли).

**Разработка интерфейса**:

```powershell
cd service; docker compose up -d                   # база + сервис + агент (или: up -d db и оба из .venv)
cd web;     npm install; npm run dev                  # http://localhost:3000, ходит к сервису на :8000
```

Скрипты `web`:

| | |
|---|---|
| `npm run dev` | dev-сервер с горячей перезагрузкой |
| `npm run generate` | статическая сборка в `web/.output/public` — её раздаёт сервис |
| `npm run api:types` | выгрузить OpenAPI сервиса и сгенерировать `app/types/bridge.d.ts` |
| `npm run typecheck` | проверка типов |

```
  stores/    brewery · recipes · preferences (Pinia)
  utils/     brew.ts (логика представления, чистые функции) · recipe.ts (рецепт ↔ форма, программа, проверка)
             beer.ts (°P ↔ SG, ABV, цвет по EBC) · styles.ts (BJCP) · additions.ts · api.ts · format.ts
  data/      bjcp-2021.json — стили BJCP 2021 и их рамки (scripts/bjcp.py, источник — beerjson/bjcp-json, MIT)
  types/     bridge.d.ts (генерируется) · index.ts · recipe.ts

```

Типы API руками не пишутся — после правок схем сервиса (`service/app/schemas.py`) запустить `npm run api:types`.

**Рецепт** описывает пиво (по мотивам BeerJSON): стиль, цели, засыпь, хмель, добавки, дрожжи, затирание, кипячение, брожение. Программа пивоварни и напоминания о закладках выводятся из него — в сервисе `service/app/program.py`, в интерфейсе `utils/recipe.ts`; правила у них одни, менять вместе. Агенту программа уходит в общем виде, в протокол пивоварни её переводит он (`agent/agent/recipe.py`). Плотность хранится в SG, показывается в °P или SG (Настройки → Единицы).

**Показатели** считаются по ингредиентам (`web/app/utils/calc.ts`), вручную не вводятся: OG — экстракт засыпи × эффективность на объём после кипячения, FG — по степени сбраживания дрожжей (по умолчанию 75 %), ABV — по OG и FG, IBU — Tinseth, цвет — Morey (EBC солода → SRM → °L). Ползунки рамок стиля в редакторе подгоняют ингредиенты: OG — всю засыпь пропорционально, IBU — горькую (самую раннюю) закладку, FG — сбраживание дрожжей, цвет — самый тёмный солод. Упрощения: выход экстракта средний по типу и цвету сырья (светлый солод 80 %, карамельный и специальный 75 %, жжёный 60 %, несоложёное 75 %, сахар 100 %, сухой экстракт 95 %); IBU считается по OG; вирпул и сухое охмеление горечи не дают. Сверено с рецептами Pils и Irish Stout из `beer/`.

**Список рецептов**: карточка — бокал по стилю BJCP в цвет пива (шкала EBC «как в бокале», `utils/beer.ts`), первый абзац описания, цифры и миниатюры фото; фото открываются прямо из списка. Высота у всех карточек одна.

**Вода** (`web/app/utils/water.ts`): заторная и промывочная вода, соли и кислоты с указанием, куда идут, исходная вода (по умолчанию осмос — нули). Профиль Ca, Mg, Na, Cl, SO₄, HCO₃ и Cl:SO₄ считается по молярным массам солей (мел — как 2 HCO₃⁻ на CaCO₃); кислоты в профиль не входят, pH затора не прогнозируется. В рецепте хранится **гидромодуль** (л/кг), литры считаются: заторная вода = гидромодуль × засыпь в затор; вся вода = объём после кипячения + испарение × время кипячения + 0,8 л/кг, которые удержит дробина; промывочная — остальное. Испарение берётся из **профиля оборудования** (Настройки → Оборудование, хранится у пивоварни; там же эффективность для новых рецептов), поэтому промывочная вода у разных пивоварен по одному рецепту разная. Удержание дробиной — константа: промывку останавливают по плотности, и расчётная промывочная вода — запас, а не норма. Тепловое расширение не учитывается: объёмы — по шкале котла, как и эффективность.
