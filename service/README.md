# service — сервис brewapp

Бэкенд приложения: рецепты, история варок, уведомления и связь с агентами пивоварен. Пивоварню сервис сам не видит — с ней говорит агент рядом с ней ([../agent](../agent/README.md)), а сервис принимает его по WebSocket. Интерфейсу сервис отдаёт:

- состояние и события пивоварни — потоком **SSE** `GET /api/stream` (`event: state` — снимок, `event: event` — событие варки);
- команды — обычными `POST` (`/api/power`, `/api/manual`, `/api/recipe/start`, …): сервис передаёт их агенту и ждёт его ответа;
- библиотеку рецептов — `GET/PUT/DELETE /api/recipes/{id}`, загрузка в пивоварню — `POST /api/recipes/{id}/upload`;
- фото пива — `GET/POST /api/recipes/{id}/photos`, картинка — `GET /api/photos/{id}` (`?thumb=true` — превью 480 px), `DELETE /api/photos/{id}`;
- историю варок — `GET /api/brews`, `GET /api/brews/{id}` (рецепт, температура, события).

Вход — по почте и паролю (`/api/auth/*`), сессия — httpOnly-cookie. Гость смотрит опубликованные рецепты; свои рецепты, пивоварня и варки — после входа; администратор ещё модерирует и раздаёт роли (`/api/admin/*`). Права — в одном месте, `app/access.py`; подробно — «Вход и роли» ниже.

Агенты подключаются к `WS /api/agent` с токеном в заголовке `Authorization: Bearer …`; формат сообщений — [agent/README.md](../agent/README.md#протокол).

Данные — в **Postgres**: пользователи, агенты, пивоварни, рецепты, варки, события, температура (см. «Данные» ниже).

Схема API — http://127.0.0.1:8000/docs (OpenAPI). Из неё генерируются TS-типы фронтенда: `cd ../web && npm run api:types`.

## Запуск

### Локально

```powershell
cd brewapp\service
copy .env.example .env                           # пароль Postgres
docker compose up -d db                          # база — в Docker (порт 5433 на этом ПК)
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m app.agents new           # токен агента — в agent\.env (AGENT_TOKEN), печатается один раз
.venv\Scripts\python -m app.server               # http://127.0.0.1:8000
.venv\Scripts\python -m app.server --lan         # + доступ с телефона: http://<IP ПК>:8000
```

Адрес базы сервис берёт из `DATABASE_URL` (окружение или `.env`). Агента запускают отдельно — [agent/README.md](../agent/README.md).

### В Docker

```powershell
cd brewapp\service
copy .env.example .env        # POSTGRES_PASSWORD
docker compose up -d --build  # db (Postgres 17) + service + agent
docker compose logs -f service
```

- Агент в `compose.yaml` — для случая, когда всё на одной машине. Его настройки — `agent/.env` (токен, `BREWERY_IP`), ключи и память — из папки `agent/`. Широковещание из сети Docker до модуля Tuya не доходит, поэтому адрес пивоварни в `agent/.env` обязателен.
- База живёт в томе `pgdata` — переживает пересборку и `docker compose down` (удаляет только `down -v`).
- Порт по умолчанию открыт только на этом ПК (`127.0.0.1:8000`). Для телефона поменять на `8000:8000` в `compose.yaml` — но входа пока нет, управлять сможет любой в Wi-Fi.

Переменные окружения: `DATABASE_URL` — база; `APP_URL`, `ADMIN_EMAILS`, `SMTP_*` — вход и письма (ниже); `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` — уведомления; `SERVICE_HOST`, `SERVICE_PORT` — где слушать; `FORWARDED_ALLOW_IPS` — за reverse proxy: чьим заголовкам `X-Forwarded-*` верить; `BREWAPP_WEB_DIR` — сборка интерфейса.

Сервис в интернете (образ с интерфейсом, сервер, CI/CD) — [deploy/README.md](../deploy/README.md).

## Вход и роли

- **Регистрация** — почта и пароль (от 8 символов; хранится хэш scrypt). Входить можно сразу; письмо со ссылкой подтверждения уходит тут же. Подтверждённая почта нужна, чтобы публиковать рецепты.
- **Сессия** — случайный токен в httpOnly-cookie (`SameSite=Lax`, `Secure` по HTTPS), в базе — его SHA-256; 30 дней с последнего захода. Новый пароль по ссылке из письма закрывает все прежние входы.
- **Письма** (`app/mail.py`) — подтверждение почты и новый пароль, ссылки одноразовые. Без `SMTP_HOST` письмо пишется в журнал сервиса — для разработки; для открытой регистрации SMTP обязателен. Ссылки ведут на `APP_URL`; без него — только на адрес этого же ПК (иначе подставной заголовок увёл бы ссылку сброса пароля на чужой сайт).
- **Подбор пароля** — не больше 10 неудачных входов в одну почту и 50 с одного адреса за 15 минут; писем со ссылками — 5 на почту в час.
- **Чужой сайт** — изменяющие запросы принимаются только со своего адреса (`APP_URL`, а без него — с этого ПК).
- **Роли** (`app/access.py`): гость — опубликованные рецепты и их фото; пользователь — свои рецепты (личные, пока он их не опубликует), своя пивоварня, варки, уведомления; администратор — ещё снять с публикации или удалить чужой опубликованный рецепт и раздать роли. Чужие личные рецепты не видит никто, администратор тоже.
- **Кто администратор**: на сервере — почты из `ADMIN_EMAILS`; у себя на ПК (без `ADMIN_EMAILS`) — первый зарегистрировавшийся. Данные, заведённые до входа (пользователь без почты), забирает регистрация администратора. Роль потом — в интерфейсе «Пользователи» или `PUT /api/admin/users/{id}/role`; последнего администратора не снять.

## Агенты

Агент — программа рядом с пивоварней. Соединение открывает он сам, поэтому сервису не нужно видеть домашнюю сеть пивовара. Пока не сделана привязка по короткому коду с сайта (этап 2, [ARCHITECTURE.md](../ARCHITECTURE.md)), токен выдаёт команда:

```powershell
.venv\Scripts\python -m app.agents new "Название"   # новый агент владельца — токен печатается один раз
.venv\Scripts\python -m app.agents list             # агенты и когда были на связи
```

В базе токен хранится только хэшем (SHA-256). Подключившись, агент сообщает, какую пивоварню обслуживает, — сервис заводит её или привязывает к агенту, запоминает модель и ограничения (по ним проверяются рецепты, пока агента нет на связи).

- **Команды** уходят только на живое соединение: агента нет — сразу `503 пивоварня не в сети`, в очередь команды не ставятся. Связь оборвалась, пока команда ждала ответа, — тоже 503, но с оговоркой: пивоварня могла команду уже выполнить. Ответ агента — как HTTP-статус: 400 — неверные данные, 404 — нет такого, 502 — пивоварня не подтвердила, 504 — не ответила.
- **Записи** агента (события, температура, варки) пронумерованы: сервис подтверждает каждую, как только принял её в журнал, а повтор после переподключения отбрасывает по номеру. В пути между агентом и сервисом записи не теряются, даже если соединение оборвалось незаметно; запись в базу дальше идёт очередью журнала, как и раньше.
- **Загруженный рецепт** поправили или удалили — сервис сообщает агенту, и тот обновляет или забывает названия шагов и закладок. Агента не было на связи — он спросит сам при подключении.

## Уведомления (Web Push)

Подсказки пивоварни, закладки, конец программы, а во время варки — ошибка, выключение и потеря связи приходят системными уведомлениями, даже когда вкладка закрыта. Включаются в интерфейсе: «Настройки → Уведомления», отдельно на каждом устройстве. В уведомлении о закладке или подсказке есть кнопка «Заложил» / «Подтвердить», она шлёт команду сервису напрямую.

- **Ключ сервера** — `VAPID_PRIVATE_KEY` в `.env`. Новый: `.venv\Scripts\python -m app.push`. Без ключа уведомления выключены (`/api/push/*` отвечают 503). Если сменить ключ, браузеры подпишутся заново при следующем открытии приложения.
- **`VAPID_SUBJECT`** — контакт владельца сервера для push-сервисов (`mailto:` или `https://`).
- Подписки хранятся в таблице `push_subscriptions`. Сервис принимает адреса только push-сервисов браузеров (Google, Mozilla, Microsoft, Apple), а отозванные подписки (404/410) удаляет сам.
- Браузер разрешает уведомления только на `localhost` или по HTTPS. На iPhone нужны HTTPS и приложение, добавленное на экран «Домой».

## Данные

```
users ─┬─ sessions                  входы: токен cookie — хэшем
       ├─ auth_tokens               ссылки из писем: подтверждение почты, новый пароль
       ├─ agents                    агенты у пивоварен: токен — хэшем, когда были на связи
       ├─ devices ─┬─ readings      температура во времени (devices.agent_id — через какой агент на связи)
       │           ├─ events        события пивоварни
       │           └─ brews         варки: рецепт (снимок), начало, конец, исход
       ├─ recipes                   рецепт целиком — JSONB (программа пивоварни выводится из него)
       │    └─ recipe_photos        фото пива: снимок и превью, подпись автора чужого фото
       └─ push_subscriptions        браузеры, подписанные на уведомления
```

- **Пивоварня** в базе — то, что нужно без агента на связи: модель, ограничения, профиль оборудования. Ключи Tuya, адрес и память о программе — только у агента.
- **Варка** открывается при запуске программы рецепта и закрывается в конце программы (`finished`) или при выключении пивоварни (`stopped`) — решает агент. Агента перезапустили посреди варки — он продолжит её, если пивоварня всё ещё в программе. Варка закончилась, пока не было связи с сервисом, — агент дошлёт её конец после переподключения. Варки, о которых подключившийся агент не знает и не досылает записей, сервис закрывает как прерванные.
- **Журнал** (температура раз в ≥2 с, события) пишется отдельным потоком: медленная или упавшая база не тормозит приём от агентов.
- **Пользователи** — регистрация по почте (выше); `sessions` и `auth_tokens` хранят только хэши токенов.
- **Рецепт** — личный или опубликованный (`recipes.visibility`, `published_at`); опубликованный видят все, править может только автор.
- **Фото** хранятся в базе (bytea) и удаляются вместе с рецептом. Интерфейс заранее уменьшает снимок до 1600 px и пережимает в JPEG (EXIF с координатами съёмки пропадает); сервис принимает JPEG, PNG и WebP до 10 МБ — тип по сигнатуре файла, — проверяет, что картинка открывается, и делает превью 480 px (Pillow). До 12 фото на рецепт.
- **Схема** меняется только миграциями Alembic (`migrations/`), они применяются при старте. После правки `app/models.py`: `.venv\Scripts\alembic revision --autogenerate -m "что изменилось"`.

## Устройство

```
app/
  access.py          роли и права: кто что видит и может — в одном месте
  auth.py            вход: регистрация, пароли, сессии, ссылки из писем, лимиты попыток, пользователи и роли
  mail.py            письма (SMTP; без него — в журнал)
  hub.py             агенты на связи: приём сообщений, последнее состояние, команды, подтверждения записей
  agents.py          токены агентов; команда new / list
  push.py            Web Push: подписки браузеров, уведомления о событиях варки (отдельным потоком)
  models.py          таблицы Postgres (SQLModel)
  db.py              подключение, миграции при старте, пользователь-владелец
  store.py           рецепты, пивоварни и журнал (запись — отдельным потоком)
  program.py         рецепт → программа пивоварни в общем виде и её проверка по ограничениям от агента
  schemas.py         Pydantic-схемы API — источник OpenAPI и TS-типов фронтенда
  server.py          FastAPI: HTTP API, SSE, WebSocket агентов; раздаёт собранный фронтенд (../web/.output/public)
  export_openapi.py  выгрузка схемы в ../web/openapi.json
migrations/          миграции Alembic
```

Сервис не вносит поправок под конкретный экземпляр или привычки пивовара: агенту уходит ровно та программа, что задана в рецепте.
